# 关键设计取舍

按"决策 → 理由 → 代价"记录，方便后来者理解为什么长这样，而不是只看到结果。

## 1. 业务层与 HTTP 框架解耦，双适配器

**决策**：业务全部放 `app/service.py`；`app/api.py`（标准库）与 `server/fastapi_app.py`（FastAPI）只做协议转换。

**理由**：约束是"本地必须能跑"。目标机器可能没有外网、pip 不通，FastAPI 装不上。
与其为了框架牺牲可运行性，不如把框架变成可替换的一层。

**代价**：同一个接口要写两遍路由（约 60 行）；SSE 在标准库下需要手写 chunked 输出。
换来的是：删掉 `_pydeps/` 仍能完整演示，换框架只改一层。

## 2. SQL 按 Oracle 11g 生成，本地转译执行

**决策**：所有 SQL 以 11g 写法生成、展示、审计；执行前由 `to_sqlite()` 转译。

**理由**：生产是 Oracle 11g，`ROWNUM`、`NVL`、`TO_DATE`、`DAYS_BETWEEN` 这些差异如果只在执行时处理，
会导致"界面显示与实际执行不一致"，审计日志失去意义。

**代价**：转译层要覆盖日期函数、分页、字符串函数；转译失败时降级。
好处是演示环境与生产看到的是同一条 SQL。

## 3. 指标声明式登记，而不是把 SQL 散在代码里

**决策**：28 个指标登记为元数据（名称、类目、单位、表达式、取数表、期间条件、维度支持），
SQL 由 `metric_sql()` 拼装。

**理由**：口径必须能"被核对"。元数据集中后，指标字典页、报告、问答、宽表构建共用一份定义，
改口径只改一处；新增指标不改代码路径。

**代价**：复杂指标（毛利率、两金占用）需要额外的派生字段与 join 描述，元数据结构会比裸 SQL 复杂。

## 4. 报告固定体例 + 10 条兜底校验，而不是"让模型自由发挥"

**决策**：正文按七章模板生成，每章「结论句 → 数据表 → 分析 → 措施」；生成后过 10 条规则。

**理由**：经营报告是给领导看的，格式稳定比文采重要；更要紧的是**不能出现编造的数字**。
校验里的 `N2 数值可追溯` 要求正文每个金额类数字都能在指标值 / 同比 / 环比 / 派生占比中找到，
否则阻断审批。为此报告生成器会把表格里每个数字登记进白名单，随报告一起落库。

**代价**：报告读起来偏"公文"，不如模型自由撰写生动；模型模式也要求保留表格数量，否则回退内置引擎。

## 5. 行级权限用 SQL 谓词注入，而不是查完再过滤

**决策**：把岗位范围翻译成 `AND` 条件，注入到 SQL 顶层 `WHERE`。

**理由**：应用层过滤容易漏（比如新增一个聚合接口忘了加），而且先查全量再过滤，日志与性能都不对。
谓词注入让"越权数据根本没有进入结果集"。

**代价**：实现上要用括号深度扫描定位顶层 `WHERE`，避免插进子查询；
对不含项目维度的查询只能拒绝执行（这是刻意的：宁可报错，不返回全量）。

## 6. 会话存 localStorage，而不是服务端

**决策**：多会话的标题、消息、身份标签存在浏览器本地；后端不保存对话。

**理由**：这是演示项目，没有用户体系与多端同步需求；服务端存会话会引入"谁的会话、能存多久、怎么清理"一堆问题。
本地存储换来"刷新不丢、零后端成本"。

**代价**：换设备不同步；清缓存即丢失；需要在导出时提供 Markdown 兜底。

## 7. 导出三格式共用一套 Markdown 解析

**决策**：`export.py` 先把 Markdown 解析成块（标题 / 引用 / 列表 / 表格 / 段落），再分别渲染成 docx、pdf、html。

**理由**：三套解析必然导致"网页分页与导出分页不一致"。共用解析后，Word 的 `page_break`、PDF 的 `PageBreak`、
HTML 的 `page-break-before` 都对齐到同一个"章节"边界。

**代价**：解析器只覆盖报告实际用到的语法（不支持嵌套列表、图片、脚注），扩展性一般。

## 8. 演示库用 SQLite，并且随仓库提交前端构建产物

**决策**：本地跑 SQLite；`web/` 构建产物入库。

**理由**：`git clone` 后能立刻 `python run.py` 看到界面，评审成本最低。构建产物的 hash 变化确实会让 diff 变吵，
但换来的是"不需要 Node 也能体验"。

**代价**：`web/` 会随前端改动产生大段 diff；如果团队协作频繁改前端，建议改为 CI 构建 + 发布产物。
